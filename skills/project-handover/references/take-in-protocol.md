# 多项目接入规范（读全部 → 决定细节 → 自动执行）

> 对应 SKILL 的 **I1–I6**。接入与交出的关键差别：**接入首先是"阅读理解 + 横向决策"，然后才是执行**；
> 而"多个项目"是常态，必须先把所有项目的信息文档读完，才允许决定接入细节。

## 一、为什么必须"先读全部"

单个项目的信息文档只描述自己；**决定接入细节所需的信号横跨多个项目**：

| 信号 | 只读一个项目会漏掉什么 |
| --- | --- |
| `resources` | 两个项目抢同一张 NPU 卡 → 若并行就互相干扰 |
| `depends_on` | A 依赖 B 的产物 → 先做 A 是错的 |
| `deadline` + `priority` | 不知道先做哪个，可能把 P0 挤到后面 |
| `verified` / `submitted` | 可能重复做已完成的事，或假设了未验证的结论 |
| 结论/红线 | 两个项目的红线可能互相冲突（同一文件被双方规定"别动"） |

**硬规则**：接入 N 个项目就必须读 N 份 `HANDOVER.md`；报告里要能证明 N/N 读过（列出每个 `project_id`）。

## 二、接入四问（决定细节的检查表）

1. **依赖序**：`depends_on` 里有谁？被依赖的是否在本次接入集合内？不在 → 报警并确认外部依赖。
2. **资源冲突**：`resources` 交集是否非空？非空 → **必须串行**，并写明串行顺序与原因。
3. **截止与优先级**：`deadline` 升序为主序，`priority` 为次序；`deadline: null` 排最后。
4. **可信度与落地状态**：`verified: false` → 执行时把它的结论当"待复核"；`submitted: false` → 需在本次接入中完成提交动作才叫接入完成。

## 二·五、独立项目目录与命名（I7 / I8）

**每个项目一个独立目录，且必须命名**——这是多项目接入不互相污染的前提。

| 项 | 规则 |
| --- | --- |
| 目录名 | = `HANDOVER.md` 的 **`project_id`**（kebab-case、唯一）；非法字符替换为 `-` |
| 兜底 | `project_id` 缺失 → 用归档文件名（去扩展名） |
| 冲突 | 目录已存在时**默认新建带日期目录** `<project_id>-<YYYYMMDD>`（绝不静默覆盖）；可切 `--on-collision update`（原地刷新，保留 `ACCESS.md`）或 `skip` |
| 解包位置 | 归档内容解到**该项目目录内**（单层顶层目录会被上提，避免多一层） |
| 归档留存 | 原始归档复制到 `<工作根>/_archives/`（改名不改内容） |
| 索引 | `<工作根>/INDEX.md`（人读）、`<工作根>/registry.json`（机器读，含来源与 SHA256） |
| 接入记录 | 每个项目目录内 `ACCESS.md`：来源归档 + SHA256 + 首次接入时间 + 已读确认 + 接入细节 + 执行日志表 |

一次性完成（I-P1）：

```bash
python3 scripts/prepare_projects.py --root ~/handover --dry-run pkg1.tar.gz pkg2.tar.gz   # 先预览命名
python3 scripts/prepare_projects.py --root ~/handover pkg1.tar.gz pkg2.tar.gz             # 建目录并解包
```

结果布局：

```
~/handover/
├── INDEX.md
├── registry.json
├── _archives/{pkg1.tar.gz, pkg2.tar.gz}
├── <project_id_1>/{HANDOVER.md, ACCESS.md, …}
└── <project_id_2>/{HANDOVER.md, ACCESS.md, …}
```

**禁止**：把两个项目解到同一目录；用 `project_id` 之外的随意名字；覆盖已有目录而不留痕。

## 三、接入计划的必备字段（必须产出）

| 字段 | 来源 |
| --- | --- |
| 项目 | `project_id` / `project_name` |
| 优先级 / 截止 | front-matter |
| 依赖 | `depends_on` |
| 独占资源 | `resources` |
| **首动作** | `next_action` |
| 串行/并行 | 由资源冲突决定 |
| **接入完成定义** | 由该项目第 1 节验收标准 + `submitted` 推出 |

## 四、自动执行的边界（I2 / I3）

**默认不停下来问**：读完 → 决定 → 直接执行第 8 节（未完成事项）与 `next_action`。

**只有这四种情况允许停下来：**

| 情况 | 处理 |
| --- | --- |
| 不可逆操作（push / 开 PR / 删除 / 覆盖既有结果） | 先说明要做什么、影响面，等确认 |
| 凭据或环境缺失且无法自行获取 | 报缺什么、怎么给 |
| 多项目信息冲突（资源/文件/依赖成环） | 列出冲突双方与两种解法，请选 |
| 信息文档缺件或格式校验不通过 | 报缺失项；不猜测内容 |

## 五、执行与回报（两阶段：自动 / 待审）

接入**不等于**立刻开工，按资源依赖分成两个阶段（详见 `references/approval-gate.md`）：

| 阶段 | 内容 | 审批 |
| --- | --- | --- |
| **A · 自动** | 信息读取 + 项目整理：读完全部 `HANDOVER.md`、建 `project_id/` 目录、解包、格式与哈希校验、写 `INDEX`/`registry`/`ACCESS`、产出接入计划、静态阅读 | 不需要 |
| **B · 待审** | 具体执行/计算/分析：编译构建、跑测试/基准/性能、训练/推理、设备占用、大规模数据处理、需要凭据或外部服务、push/PR/部署、删除或覆盖 | **必须先汇报，审核通过后执行** |

- 阶段 B 的每一项都写成审批单（`<工作根>/APPROVALS.md`，并在该项目 `ACCESS.md` 记一行 `pending`），包含：命令、资源占用、依赖的机器配置、风险与回滚、预期产物、不执行的后果。
- **未获批不得执行**，也不得"先跑一下试试"；获批范围即边界，超出需重新申请。
- **不确定归入阶段 B**（默认从严）。
- 获批执行后按四件套回报：**命令 / 原始日志路径 / 结论（达标或不达标）/ 下一步**；共享独占资源的项目串行，并在日志里贴出串行证据。

## 六、多项目接入报告模板

```
【接入完成】共 N 个项目：<ids>
读取情况：HANDOVER.md N/N 已读；格式校验 <通过/失败>；自检 <通过/失败>
接入顺序：<id1> → <id2> → …     理由：<依赖序 / 截止 / 优先级 / 资源串行>
资源串行：<resource> 被 <id1,id2> 共用 → 串行（<顺序>）
依赖处理：<id3> 依赖 <id4>（<在集合内/外部>）
阶段 A 已完成（资源无关）：<建目录 / 索引 / ACCESS / 接入计划>
待审（阶段 B，尚未执行）：<AR-编号 — 项目 — 操作 — 资源占用 — pending>
已获批并执行：
  - <id>：<动作> — `<命令>` — <结论>
阻塞：
  - <id>：<原因> — 需要 <输入>
下一个动作：<具体；若要开工请批准 AR-xxx>
证据：<日志路径列表>
```
